## 2. How a Backend API Works (Quick Crash Course)

Think of a backend API like a **restaurant**:

1. **Customer walks in and makes a request** → The frontend sends an HTTP request (e.g. `POST /favorites`)
2. **Host checks your reservation** → Middleware/dependencies verify your JWT token (are you logged in?)
3. **Waiter takes your order** → The **router** receives the request and validates the data shape
4. **Kitchen cooks the food** → The **service** runs the business logic (save to DB, check for duplicates, etc.)
5. **Food comes back on a plate** → The **schema** formats the response so the frontend gets a clean JSON object

In code terms, every API request flows through these layers:

```
Frontend Request
    ↓
  Router        (receives the request, validates input shape)
    ↓
  Dependency    (checks JWT token → extracts user_id)
    ↓
  Service       (business logic — talks to the database)
    ↓
  Model         (defines what the database table looks like)
    ↓
  Schema        (defines what the request/response JSON looks like)
    ↓
  Response back to Frontend
```

## 4. How the Files Work Together

### The foundation layer (runs once at startup)

| File | What it does |
|------|-------------|
| **config.py** | Reads `.env` file → provides settings like `DATABASE_URL`, `JWT_SECRET_KEY`, `GOOGLE_CLIENT_ID` everywhere in the app |
| **database.py** | Creates the connection to PostgreSQL. Provides a `get_db` function that gives each request its own database session |
| **main.py** | Creates the FastAPI app, registers all routers (`auth`), and auto-creates database tables on startup |

### The request flow (happens on every API call)

| Step | File | Role |
|------|------|------|
| 1 | **routers/auth.py** | Receives the HTTP request. Defines the URL path, HTTP method, and what schema to expect |
| 2 | **schemas/auth.py** | Validates the incoming JSON body (e.g. "email must be a valid email", "password needs 8+ chars with uppercase, number, special char") |
| 3 | **dependencies.py** | For protected endpoints — extracts the JWT token from the `Authorization` header, decodes it, returns the `user_id` |
| 4 | **services/auth_service.py** | Does the actual work — queries the database, hashes passwords, checks for duplicates, creates records |
| 5 | **models/user.py** | Defines the database table structure (columns, types, constraints) so SQLAlchemy can read/write rows |
| 6 | **utils/jwt.py**, **email.py**, **google_oauth.py** | Helper functions used by services — token generation, email sending, Google token verification |

### Visual: a request to `POST /auth/signin`

```
Frontend: POST /auth/signin  { email: "user@example.com", password: "MyPass1!" }
  │
  ▼
routers/auth.py              → "this is a POST to /auth/signin, no JWT needed"
  │
  ▼
schemas/auth.py              → validates body has email (valid format) and password (string)
  │
  ▼
services/auth_service.py     → finds user in DB, verifies password hash, issues JWT tokens
  │
  ▼
models/user.py               → defines the users table (id, email, name, password_hash, ...)
  │
  ▼
Response: 200  { token: "jwt...", refreshToken: "jwt...", user: { id, email, name } }
```

## 5. APIs We Built

### Auth APIs (10 endpoints)

All under `/auth` — handle user registration, login, and session management.

| # | Method | Endpoint | What it does | Auth required? |
|---|--------|----------|-------------|----------------|
| 1 | POST | `/auth/signup` | Create a new account (email + password + name). Sends a 6-digit verification code to email | No |
| 2 | POST | `/auth/verify-email` | Submit the 6-digit code to verify email address | No |
| 3 | POST | `/auth/resend-code` | Resend verification code (30s cooldown between resends) | No |
| 4 | POST | `/auth/signin` | Log in with email + password. Returns JWT access token + refresh token | No |
| 5 | POST | `/auth/google` | Log in with Google. Sends a Google ID token, backend verifies it and creates/finds the user | No |
| 6 | POST | `/auth/forgot-pw` | Request a password reset code (sent to email) | No |
| 7 | POST | `/auth/reset-pw` | Submit the reset code + new password to change password | No |
| 8 | POST | `/auth/refresh-token` | Exchange an expiring refresh token for new access + refresh tokens | No |
| 9 | POST | `/auth/logout` | Revoke all refresh tokens for the user | **Yes** |
| 10 | GET | `/auth/me` | Get the current logged-in user's profile (id, email, name) | **Yes** |

## 6. Database Tables We Created

| Table | Purpose | Key columns |
|-------|---------|-------------|
| **users** | Stores user accounts | `id` (UUID), `email`, `name`, `password_hash`, `provider` ("email" or "google"), `is_verified` |
| **verification_codes** | Temporary 6-digit codes for email verification & password reset | `email`, `code`, `code_type`, `expires_at` |
| **refresh_tokens** | Tracks issued refresh tokens so we can revoke them on logout | `user_id`, `token`, `is_revoked`, `expires_at` |
